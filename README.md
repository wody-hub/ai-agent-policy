# AI Agent Policy

Codex·Claude Code의 전역 모델 운영 전략, Orca 프로젝트별 실행 전략, 프로젝트 Task·문서·브랜치 관리 정책을 공유하는 저장소입니다. 전략과 선택 이유는 이 README에서 설명하고, 실제 설치 지시는 네 파일로 제공합니다.

기준일: **2026-10-07**. 모델·추론 수준·실행 기능은 계정과 제공자, 설치 버전에 따라 달라지므로 적용할 때 다시 확인합니다.

### 빠른 설치

1. 위 링크에서 필요한 파일을 내려받거나, 아래 명령으로 저장소를 복제합니다. 복제한 저장소는 설치 지시서를 보관하는 위치이며 프로젝트 정책을 설치할 대상은 별도로 지정합니다.

   ```bash
   git clone https://github.com/wody-hub/ai-agent-policy.git
   ```

2. Codex·Claude 전역 정책은 해당 도구에서 파일 안의 **설치 프롬프트 코드 블록 전체**를 입력합니다. 또는 파일을 첨부하거나 로컬 경로로 읽게 한 뒤 아래 요청을 사용합니다.
3. Orca·Task 정책은 **적용할 프로젝트**에서 요청합니다. 프로젝트 그룹이면 대상 저장소들과 문서 저장소를 함께 알려주세요. 파일별로 순서대로 설치하고 설치 보고를 확인합니다.
4. 설치 후 새 세션에서 지침 로딩과 유효 설정을 확인합니다. Orca는 dev 반영·새 워크트리 로딩·지원되는 실행 검사 상태를, Task는 작은 업무의 등록·브랜치 매핑·검증 기록·문서 커밋 흐름을 확인합니다. 실행하지 않은 검사는 미검증으로 남깁니다.

파일을 읽게 한 뒤 사용할 요청 예시입니다. 해당 파일 한 개를 선택해 요청하세요.

| 선택한 파일 | 요청 예시 |
| --- | --- |
| Codex 전역 | 이 파일을 끝까지 읽고 내 Codex 전역 모델 운영 지침으로 설치해줘. 기존 설정을 백업·보존하고 새 세션의 적용 방식과 실제 확인 결과를 알려줘. |
| Claude 전역 | 이 파일을 끝까지 읽고 내 Claude Code 전역 모델 운영 지침으로 설치해줘. 기존 설정을 백업·보존하고 새 세션의 적용 방식과 실제 확인 결과를 알려줘. |
| Orca 프로젝트 | 이 파일을 끝까지 읽고 현재 프로젝트에 Orca 전략을 설치해줘. 기존 전역 지침을 유지하고 dev·부모 작업공간·지원 기능을 확인한 뒤 설치 상태를 구분해 알려줘. |
| Task 프로젝트 | 이 파일을 끝까지 읽고 현재 프로젝트에 Task 관리 정책을 설치해줘. 문서 정본 위치와 브랜치 연결을 확인하고, Orca 정책이 있으면 연동하고 없으면 Task 정책만 설치해줘. |

파일을 읽거나 저장소를 내려받는 것만으로 설치되지는 않습니다. 에이전트가 파일 안의 설치 지시를 수행해야 적용됩니다. 범용 자동 설치·업데이트 스크립트는 제공하지 않습니다. 기존 설치를 갱신할 때도 최신 파일을 다시 적용하고 변경 diff와 보고를 확인합니다.

### 네 정책의 독립 설치와 조합

각 파일은 독립적으로 설치할 수 있습니다. 모두 사용할 경우 역할이 맞물리며, 빠진 정책을 자동 설치하거나 그 정책이 있다고 가정하지 않습니다.

| 설치한 정책 | 동작하는 범위 | 추가하지 않는 동작 |
| --- | --- | --- |
| Codex만 | Codex 모델·추론·위임 전략 | Claude 설정, Orca 작업공간, Task 폴더 설치 |
| Claude Code만 | Claude 모델·추론·개인 에이전트 전략 | Codex 설정, Orca 작업공간, Task 폴더 설치 |
| Orca만 | dev 자식 워크트리와 사용 가능한 모델 후보 배정 | 전역 모델 지침 변경, 별도 Task 문서 정책 설치 |
| Task만 | 업무 기록·문서 정본·브랜치 연결·허용된 문서 커밋 | dev 강제, Orca 실행, 모델 설정 변경 |
| 네 정책 모두 | 모델 선택 + dev 작업공간 + 업무 추적·문서 커밋 | 설치 범위를 넘는 자동 게시·병합·배포 |

권장 설치 순서는 사용하는 도구의 전역 정책 → 프로젝트 Orca 정책 → Task 정책입니다. 다른 순서로 설치해도 관리 블록과 담당 영역을 보존해야 합니다. 두 전역 정책은 해당 CLI를 사용하는 경우에만 적용됩니다. Orca에서는 프로젝트의 교차 도구 구현 배정 정책이 더 구체적으로 적용되며, 시스템·개발자·조직 제한은 그대로 따릅니다.

적용 시 Orca 업무 여부와 현재 역할(Main·Controller·Worker)을 먼저 확인합니다. 상위 지침을 지키면서 모델 운영은 해당 전역 정책, Orca 실행 위치·역할·통합 후보 선택은 Orca 정책, 업무 기록·브랜치 연결·문서 커밋은 Task 정책을 따릅니다. Worker에게 지휘자의 배정 규칙을 재귀적으로 적용하지 않습니다.

조합 실행은 `업무 ID 결정 → 문서 위치 확인 → dev 자식 워크트리 생성·검사 → Task 등록·브랜치 매핑 → Worker 배정 → 구현·검증 → 기록 갱신·문서 커밋 → 결과 보고`입니다. 최초 Task 기록을 위한 문서 작업공간 준비와 최소 등록·매핑은 부트스트랩으로 허용합니다. Orca에서는 Controller가 검증된 문서 작업 워크트리에서 이 최소 기록만 작성할 수 있으며, 공통 workspace·기본 dev 수정과 등록 전 업무 코드·최종 산출물 수정·검증은 허용하지 않습니다.

## 공통 운영 원칙

비용이 낮은 모델의 호출 횟수를 늘리는 것보다 **정확성을 유지하면서 전체 사용량과 완료 시간을 줄이는 것**을 목표로 합니다. 전체 비용에는 실행, 맥락 전달, 재시도, 검토, 통합이 모두 포함됩니다.

- 작고 현재 맥락에서 바로 끝낼 수 있는 작업은 Orca 밖에서는 메인이 직접 완료합니다. Orca 업무는 관리되는 Worker가 직접 실행하며 Main·Controller는 조율과 최소 Task 등록 부트스트랩을 맡습니다.
- 목표·완료 조건·인터페이스가 명확하고 검증 가능한 기능은 실행자에게 맡깁니다. 파일 수만으로 승격하지 않습니다.
- 불명확한 원인, 공유 상태, 동시성, 구조 변경과 높은 실패 영향은 전문 판단이 필요한 작업으로 분류합니다.
- 일반 인계에는 목표, 관련 맥락, 담당 파일·책임, 인터페이스, 제약, 완료 조건을 전달합니다.
- 실패 승격에는 문제, 관련 파일·구조, 증거, 시도와 결과, 현재·대안 가설, 필요한 판단을 추가합니다.
- 동일 실행자의 같은 원인에 대한 구현·수정은 최초 시도와 증거 기반 추가 수정 1회, 총 2회까지입니다. 이후 자동 재시도를 중단하고 책임자가 새 근거·가설·검증 계획으로 재진단하여 추가 실행 여부를 결정합니다. 모델 교체만으로 횟수를 초기화하지 않습니다. 책임자가 이미 실행 중이면 자체 재진단 또는 독립 자문을 수행합니다. 구조적 위험·요구사항 모순·데이터 무결성 위험은 즉시 책임자에게 전달합니다.
- 도구·권한·환경 장애와 모델 추론 실패를 구분합니다. 모델을 바꾸는 것만으로 환경 문제를 해결하려 하지 않습니다.
- 진단한 책임자가 바로 수정하는 편이 효율적이면 재위임하지 않습니다.
- 기본은 메인과 작업자 1개이며, 독립 작업의 실익이 있을 때만 병렬 실행합니다. 실제 런타임 제한을 따릅니다.
- 공통 계약과 파일 소유권을 먼저 정하고 다른 작업자의 변경을 되돌리지 않습니다. 불필요한 중첩 위임과 전체 저장소 재탐색을 줄입니다.
- 완료는 실제 검증 결과와 요구사항 충족으로 판단합니다. 입력 수락, 작업 시작, 실행 중, 검토 대기, 완료를 구분합니다.
- 모델 이름·역할 이름·요청한 인수만으로 실제 모델 전환을 주장하지 않습니다.

인증·인가, 암호화, 운영 인프라, 파괴적 데이터 작업과 데이터 손실 위험이 있는 마이그레이션은 전문 분석·검토를 먼저 거칩니다. 대상, 복구 방법과 데이터 무결성 확인 방법을 확정하고, 실패 영향이 매우 크면 독립 검토를 추가합니다. 설치 승인을 운영 배포나 권한 우회, 추가 유료 크레딧 사용의 승인으로 취급하지 않습니다.

## Codex 전략

**Sol이 판단·통합을 맡고, Luna가 명확한 기능을 구현부터 검증까지 책임지는 균형형 전략**입니다. Luna를 반복 작업에만 제한하지 않고, 기존 패턴과 계약이 명확한 중간 규모 기능까지 맡깁니다.

| 책임 | 모델 | 초기 추론 수준 |
| --- | --- | --- |
| 메인·요구사항·통합·최종 검토 | `gpt-6.1-sol` | `medium` |
| 기능 구현·관련 검증 | `gpt-6-luna` | `high` |
| 좁은 탐색·로그 정리·정형 변환 | `gpt-6-luna` | `medium` |
| 어려운 진단·상태·동시성·구조 변경 | `gpt-6.1-sol` | `high`, 필요 시 `xhigh` |
| 예외적인 전문가 판단 | `gpt-6-astra` | 판단에 따라 `medium` 또는 `high` |
| 선택적 독립 검토 | 사용 가능한 Claude 모델 | 실제 지원 수준 |

```text
Sol이 범위·공통 계약·완료 조건 정의
  → Luna high 구현·검증
  → Sol이 diff·검증 근거·통합 동작 검토

불명확하거나 결합이 높은 문제
  → Sol high가 진단·실행
  → 필요한 경우에만 Astra 또는 Claude 검토
```

Senior Sol은 다른 모델이 아니라 추론 수준을 높인 전문 역할입니다. Luna → Senior Sol → Astra를 모든 작업의 필수 경로로 만들지 않습니다. 작은 작업은 직접 완료하고, Sol이 이미 맥락을 이해한 복잡한 작업도 직접 처리할 수 있습니다.

이 배분의 근거는 Luna의 집중된 작업에 대한 효율성과 6.1 Sol의 복잡한 작업에 대한 역할입니다. 공식 Codex 문서는 Luna의 시작 추론 수준으로 high를 안내합니다. 역할별 담당 범위 확대는 프로젝트에서 평가할 운영 제안이며 Luna가 모든 작업에서 Sol과 같다는 주장은 아닙니다. [공식 모델 안내](https://learn.chatgpt.com/docs/models), [서브에이전트 안내](https://learn.chatgpt.com/docs/agent-configuration/subagents)

### Codex 적용 위치와 확인

전역 지침은 유효한 `CODEX_HOME`의 `AGENTS.md`, 모델 기본값은 같은 위치의 `config.toml`에 반영합니다. 기본 디렉터리는 `~/.codex`입니다.

기본 설정은 메인 Sol medium, 서브에이전트 Luna high이며 단순 조사에는 medium을 명시합니다. 환경이 지원하면 동시 서브에이전트 상한을 3개로 설정합니다. `AGENTS.override.md`, 프로젝트 지침과 사용자 지정 에이전트 설정이 적용을 바꿀 수 있으므로 확인합니다.

파일 수정과 새 세션의 유효 설정 확인은 구분합니다. 현재 메인 모델은 정책 문구만으로 바뀌지 않습니다. [전역 지침 로딩](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## Claude Code 전략

**Opus가 판단·통합을 맡고, Sonnet이 명확한 기능을 구현·검증하는 전략**입니다. Sonnet의 기본 실행과 정밀 검증을 구분하며 Haiku는 단순 조회, Fable은 예외적 자문에 사용합니다.

| 책임 | 기준 모델 ID | 초기 추론 수준 |
| --- | --- | --- |
| 메인·요구사항·통합·최종 검토 | `claude-opus-5-5` | `medium` |
| 명확한 기능 구현·관련 검증 | `claude-sonnet-5-5` | `medium` |
| 재현 가능한 버그·경계 조건·정밀 검증 | `claude-sonnet-5-5` | `high` |
| 파일 탐색·정형 추출·짧은 요약 | `claude-haiku-4-5-20251001` | effort 지정 안 함 |
| 불명확한 진단·상태·동시성·구조 변경 | `claude-opus-5-5` | `high`, 필요 시 `xhigh` |
| 예외적 자문·장기 맥락의 난제 | `claude-fable-5-1` | `high` |
| 선택적 독립 검토 | 사용 가능한 Codex 모델 | 실제 지원 수준 |

```text
Opus가 범위·공통 계약·완료 조건 정의
  → Sonnet medium 구현·검증
  → Opus가 diff·검증 근거·통합 동작 검토

검증 요구가 높거나 경계 조건이 많은 작업
  → Sonnet high

불명확하거나 결합이 높은 문제
  → Opus high가 진단·실행
  → 필요한 경우에만 Fable 또는 Codex 검토
```

Opus는 관리만 하는 모델이 아닙니다. 이미 진단한 문제를 직접 수정하는 편이 효율적이면 완료까지 맡습니다. Fable은 출시 순서나 이름만으로 모든 작업에서 우월하다고 가정하지 않으며 필수 승격 단계로 두지 않습니다. 기본 Fable 자문에는 쓰기·실행 권한을 부여하지 않습니다.

### Claude 모델 근거와 기존 전략의 변경

2026-10-07 공식 목록에서 확인한 운영 후보는 Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 4.5입니다. 확인 환경은 Claude Code 2.1.290이었으며, 최소 읽기 전용 호출에서 sonnet과 opus가 각각 `claude-sonnet-5-5`, `claude-opus-5-5`로 응답했습니다. Fable·Haiku는 이 확인 과정에서 실제 호출하지 않았습니다. 이 결과는 해당 환경의 접근 확인이며 구현 성능 평가가 아닙니다. [공식 모델 목록](https://platform.claude.com/docs/en/models/overview)

기존 Opus 5·Sonnet 5 기준을 갱신하고, Claude Code의 Opus 5.5·Sonnet 5.5 기본값인 medium에서 시작합니다. 버그·경계 조건·검증 요구에 따라 high를 선택합니다. API 문서의 기본 추론값을 Claude Code 설정에 그대로 대입하지 않으며 별칭의 제공자별 해석을 확인합니다. [Claude Code 모델 설정](https://code.claude.com/docs/en/model-config)

단순 작업의 강제 인계와 모호한 재시도 횟수를 없애고, 자문과 실행의 권한을 분리합니다. Codex의 Terra 등 고정 계층 대신 실제 사용 가능한 모델을 확인해 독립 검토를 배정합니다.

### Claude 적용 위치와 에이전트

사용자 지침은 `~/.claude/CLAUDE.md`, 설정은 `~/.claude/settings.json`, 개인 에이전트는 `~/.claude/agents/`에 반영합니다. 실제 설정 디렉터리를 먼저 확인하고 개인 지침의 관리 영역만 갱신합니다.

권장 에이전트는 sonnet-engineer(medium), sonnet-debugger(high), haiku-worker, opus-lead(high 자문), opus-specialist(high 실행), fable-advisor(high 자문)입니다. 자문은 Read·Grep·Glob만 허용하고 Bash·Edit·Write나 쓰기 MCP 권한을 허용하지 않습니다. 실행자는 승인된 수정·검증에 필요한 도구만 사용합니다. [커스텀 서브에이전트](https://code.claude.com/docs/en/sub-agents)

모델은 지원되는 model 설정, 추론은 현재 버전의 모델별 설정으로 저장합니다. 최상위 effortLevel만으로 최신 모델에 적용된다고 가정하지 않습니다. 조직 정책, 환경 변수와 프로젝트 설정이 이를 덮어쓸 수 있으며 기존 세션 재개·safe/bare 모드는 일반 새 세션과 다를 수 있습니다. CLAUDE.md는 행동 지침이며 모델·권한을 강제하는 설정은 아닙니다. Agent Teams·Ultracode는 설치 과정에서 자동 활성화하지 않습니다. [지침 로딩](https://code.claude.com/docs/en/memory), [설정 우선순위](https://code.claude.com/docs/en/settings)

## Orca 전략

**dev 아래의 작업 워크트리에서만 업무를 실행하고, Codex·Claude 모델을 하나의 후보군으로 선택하는 프로젝트별 전략**입니다. 기존 전역 지침은 유지하며 Orca 업무에 더 구체적인 실행·모델 배정 정책을 적용합니다.

### dev 기준과 부모 관계

```text
공통 workspace                     ← 요구사항·조율·상태 조회
├── 문서 저장소
│   └── dev                        ← 기준 워크스페이스
│       ├── 문서 업무 A
│       └── 문서 업무 B
├── backend
│   └── dev
│       └── 기능 업무 A
└── frontend
    └── dev
        └── 기능 업무 A
```

Git 분기 기준과 Orca 화면의 부모 관계는 별개의 조건입니다. 생성 전 dev 기준 SHA를 확정하고 생성 직후 초기 HEAD를 확인하는 동시에, parentWorktreeId가 해당 저장소의 dev 워크스페이스인지 확인합니다.

- 새 업무는 dev 기준 새 Orca 관리 워크트리, 같은 업무의 후속 작업은 기존 워크트리를 사용합니다.
- 기능 브랜치에서 요청해도 새 업무는 dev 아래의 형제 자식으로 생성합니다. 현재 기능 브랜치에서 다시 분기하지 않습니다.
- 공통 workspace는 조율용입니다. 업무 산출물 수정·구현·테스트는 작업 워크트리에서 수행합니다.
- 기본 dev 체크아웃에서 일반 업무를 수정하지 않습니다. dev가 없거나 기준·부모를 확인할 수 없으면 중단하고 main/master로 자동 대체하지 않습니다.
- 로컬·원격 dev 차이를 확인하고 기준을 기록합니다. 강제 reset·checkout이나 미커밋 변경 정리로 조건을 맞추지 않습니다.
- 여러 저장소 업무는 저장소별 하위 작업·워크트리·기준 SHA를 기록하고 하나의 업무 TASK_ID로 연결합니다. Orca Task가 생성되면 업무 TASK_ID와 구분해 매핑합니다.

### 도구 구분 없는 모델 배정

Main은 사용자 의도와 최종 판단, Controller는 Orca 조회·작업 위치·모델 선택·배정·결과 회수, Worker는 실제 조사·구현·문서·검증을 맡습니다. 실제 업무 실행을 Orca의 관리 밖에서 수행해 작업자 추적을 우회하지 않습니다. 배정 규칙은 Main·Controller에 적용하고 Worker는 담당 범위를 직접 실행합니다. Worker의 재위임에는 Main·Controller의 명시적 승인과 추적 가능한 실행이 필요합니다. 단순 질의 응답·정책 읽기·조율·상태 조회에는 Worker 생성을 요구하지 않습니다.

| 역할 | 통합 후보군 |
| --- | --- |
| 좁은 탐색·추출 | Luna medium, Haiku |
| 명확한 기능 구현 | Luna high, Sonnet 5.5 medium |
| 버그·검증이 중요한 구현 | Luna high, Sonnet 5.5 high |
| 어려운 진단·복잡한 통합 | Sol 6.1 high, Opus 5.5 high |
| 예외적 중요 판단 | Astra, Fable 5.1 |

Codex 지휘자가 Claude Worker를 선택할 수 있고, Claude 지휘자도 Codex Worker를 선택할 수 있습니다. Orca 정책은 양쪽 도구의 구현·검증 배정을 명시적으로 허용합니다. 상위 시스템·개발자·조직 정책과 실행 권한은 넘지 않으며 Orca 밖에서는 기존 전략을 유지합니다. 고위험 작업의 분석·검토도 선택한 Sol high 또는 Opus high가 담당합니다. 두 계열을 모두 필수 검토자로 요구하지 않으며 위험에 따라 독립 전문가 검토를 추가합니다.

선택은 접근·설치·실행 호스트·필요 도구를 지원하는 후보 중에서 작업의 불명확성·결합·검증 가능성·실패 영향과 유사 업무의 성공 기록으로 결정합니다. 기록이 없으면 낮은 전체 비용으로 성공할 가능성이 높은 후보를 선택합니다. 브랜드별 고정 순위나 특정 유형의 무조건적 우열을 만들지 않습니다. 요청값과 실제 실행된 도구·모델·추론 수준, 선택 이유를 기록합니다.

모델 교체는 기존 워크트리와 변경을 보존하면서 목표·diff·검증 결과·실패 가설을 인계하는 절차입니다. 동일 파일의 쓰기 책임자는 한 명이며 기존 실행의 종료·정리가 불확실하면 새 쓰기 작업자를 시작하지 않습니다. 타임아웃을 종료 증거로 취급하지 않습니다. 해당 실행의 종료·settlement/release 상태 또는 확인된 프로세스 종료·잔여 쓰기 부재를 확인하고 필수 Orca 정리를 마쳐야 교체할 수 있습니다. 수동 종료도 대상·시점·방법과 가능한 런타임 상태를 대조하며 종료나 잔여 상태가 불확실하면 교체를 차단합니다.

### 설치와 실행 차단

프로젝트 정책은 docs/orca 아래 정본과 루트 AGENTS.md·CLAUDE.md의 관리 블록으로 연결합니다. 기존 orca-setup 산출물과 프로젝트 보정은 보존합니다. Claude는 상대 경로 @import, Codex는 첫 업무 행동으로 정책 원문을 읽는 규칙을 사용합니다.

여러 저장소에서는 공통 문서 저장소의 정본을 관리하되 각 저장소에는 버전이 고정된 정책 사본 또는 검증된 스냅샷을 제공합니다. 다른 업무 워크트리의 변경 가능한 문서를 직접 참조하지 않습니다.

실행 검사는 생성 전 dev·부모·모델 접근과 업무 ID·문서 위치·예정 브랜치 확인, 생성 후 실제 워크트리·브랜치 확인, setup 성공 확인, Task 등록·매핑 확정, Worker 시작·수정 위치 확인으로 나눕니다. Task 관련 조건은 해당 정책이 있을 때만 적용합니다. 생성 전에 아직 없는 실제 workspace ID·신규 Task 기록을 요구하지 않고 Worker 배정 전에 등록·실제 매핑을 요구합니다. 신규 브랜치 이름은 Controller가 생성 시 지정하고 자동 명명 결과는 첫 업무 수정·커밋·Worker 배정 전에 안전하게 보정·재검사합니다. 지원되지 않으면 차단하며 신규 업무를 legacy mapping으로 우회하지 않습니다. 중앙 시작 경로와 각 도구에서 지원하는 검사로 실패 시 업무를 막습니다. .orca에는 실제 버전이 지원하는 설정만 두고 존재하지 않는 형식을 만들지 않습니다.

지침만으로 모든 경로의 강제를 보장하지 않습니다. 문서 적용, 중앙 시작 검사, 도구별 수정 차단을 구분하고 지원되지 않는 경로를 보고합니다. 작업공간이 분리돼도 DB·포트·외부 시스템은 별도로 충돌을 확인합니다.

최초 설치·정책 복구는 검토된 설치 지시서를 전달받은 Orca 관리 설치 Worker가 수행합니다. Orca 뒤 Task 정책 설치·갱신도 같은 설치 전용 경로를 사용하며 Orca의 dev 반영이 대기 중이면 같은 설치 업무의 검증된 워크트리를 재사용하거나 제한된 설치 경로로 준비합니다. 생성 예정 정책·진입·검사 파일 부재와 그 부재에 따른 로딩 실패만 제한적으로 허용하고 dev·부모·위치·기존 권한·실행 환경 검사는 유지합니다. 수정 범위는 설치 파일과 필요한 최소 설치 Task 기록이며 업무 소스·DB·운영 변경은 금지합니다. 생성 후 재검사하고 전용 실행 종료와 함께 예외를 종료합니다. 이 제한을 지원할 수 없으면 차단 상태로 보고합니다.

설치 변경도 dev 기준 작업 워크트리에서 준비합니다. 커밋되지 않은 지침은 새 워크트리에 상속되지 않으므로 기준 dev에 반영된 뒤 새 워크트리에서 로딩을 검증해야 합니다. dev 병합·푸시·운영 배포는 설치와 별도로 승인된 범위를 따릅니다. 파일 설치, dev 반영, 자동 인식, 실행 차단 검증의 완료 상태를 각각 보고합니다.

Orca 명령은 선택한 실행 파일의 `skills get orca-cli`와 필요한 orchestration 가이드로 확인합니다. 요청한 모델·부모 관계만으로 실행 성공을 보고하지 않습니다.

## 프로젝트 Task·문서·브랜치 전략

**실제 AI 업무는 같은 Task ID로 요구사항·설계·계획·실행·리뷰·검증·커밋을 연결하고, 기록과 실제 브랜치가 일치해야 시작·완료할 수 있습니다.** 작업자는 문서 관리를 선택 사항으로 취급하거나 다른 모델·스킬을 이유로 생략하지 않습니다. 단순 질문·조회만 하는 대화는 새 폴더를 만들지 않으며 실제 변경·공유 산출물 업무로 전환되기 전에 등록합니다.

기존 지침 생성 키트에서 문서 저장소·Task 분해·루트 진입 연결 방식을 확인했고, 적용된 산출물 정책에서 업무 ID별 정본, 로컬 초안·증거 분리, 세션 시작 확인과 관련 저장소·브랜치 기록 방식을 확인했습니다. 이 설치 정책은 그 구조를 일반화하고 **Task와 실제 브랜치의 필수 연결, 문서 커밋과 완료 게이트**를 추가합니다. 특정 프로젝트의 도메인 문서·경로·관례를 다른 프로젝트에 복사하지 않습니다.

### 그룹과 단일 프로젝트의 문서 위치

| 구조 | 공유 정본 | 로컬 전용 |
| --- | --- | --- |
| 프로젝트 그룹 | 확인한 문서 Git 저장소의 기존 업무 경로 또는 `docs/tasks/<TASK_ID>/` | 접근 가능한 업무 작업공간의 `.local-artifacts/tasks/<TASK_ID>/` |
| 단일 Git 프로젝트 | 같은 저장소의 기존 업무 경로 또는 `docs/tasks/<TASK_ID>/` | 해당 작업공간의 `.local-artifacts/tasks/<TASK_ID>/` |

그룹의 문서 저장소가 불명확하면 임의 저장소를 선택하거나 조용히 단일 방식으로 바꾸지 않습니다. 기존 도메인 원본·납품 문서·ADR·도구 상태 파일은 유지하고 Task 색인에서 연결합니다. 초안·원시 로그·추출물은 로컬에 두고 정제한 팀 공유 문서만 커밋합니다.

### Task ID와 브랜치 추적

기존 업무 ID를 재사용하고 신규 기본값은 `YYYY-MM-DD-<목적-slug>`입니다. 새 업무 브랜치는 프로젝트에서 확정한 패턴에 같은 ID를 포함합니다. 코드·문서 저장소의 prefix는 달라도 같은 업무로 찾을 수 있습니다.

```text
TASK_ID: 2026-10-07-example-feature

문서 저장소  → docs/2026-10-07-example-feature
backend      → feature/2026-10-07-example-feature
frontend     → feature/2026-10-07-example-feature

공유 기록: 문서 저장소/docs/tasks/2026-10-07-example-feature/README.md
```

Task README와 공용 색인은 배정 시 담당자를 지정합니다. 비담당 Worker는 변경·검증·커밋 요약을 전달하고 담당자만 공유 기록을 갱신·커밋합니다. Orca에서는 Controller가 결과를 회수해 문서 담당 Worker에게 전달하며, 수신과 실제 반영·커밋을 구분합니다. 단독 정책에서는 현재 Agent가 문서 담당자일 수 있습니다.

Task README에는 목적·요구 출처·완료 조건·담당·수정 범위와 저장소별 실제 브랜치, 생성 기준 ref/SHA, 소유 범위, 확인한 커밋·PR을 기록합니다. 문서 저장소도 수정 대상 행으로 포함합니다. 개인 worktree 경로·Orca workspace/터미널 ID는 로컬 실행 기록에 두고 공유 문서는 저장소·브랜치·업무 ID로 찾을 수 있게 합니다.

업무 TASK_ID와 Orca Task/Run/Dispatch ID는 별개이며 연결표로 대응합니다. 기존 브랜치 이름에 ID가 없으면 변경과 이름을 보존하고 명시적 legacy mapping을 기록합니다. 신규 업무의 규칙을 맞추기 위해 기존 작업을 강제 rename하지 않습니다.

### 생략할 수 없는 시작·완료 조건

- 시작 전 정책 원문, Task 기록, 문서 정본, 실제 저장소·브랜치와 수정 범위를 확인합니다. 필수 기록·매핑이 없거나 원본에 접근할 수 없으면 의존 업무를 시작하지 않습니다.
- 범위·담당·모델·검증이 바뀌면 해당 체크포인트에서 기록을 갱신하고 인계 시 같은 업무 ID를 전달합니다. 브랜치·워크트리 전환은 현재 매핑 유지·예정 기록 → 업무 중지 → 전환·실제 checkout 확인 → 매핑 확정 후 재개 순서입니다. 실패하면 실제 상태로 매핑을 복구하고 차단 상태를 기록합니다. 전환 중에는 기록된 예정 대상에 대한 비강제 브랜치·작업공간 전환과 확인·매핑 확정·복구를 허용합니다. 구현·검증과 위치 검사 우회는 허용하지 않습니다.
- 완료 전 검증 결과와 제한, 관련 저장소의 변경·커밋, 공유 문서 갱신·커밋 상태를 확인합니다. 문서 커밋 외 완료 조건을 충족하면 최종 커밋용 완료 상태를 작업본에 준비하되 해당 문서 커밋 성공 시 확정 조건을 표시합니다. 커밋 성공·필요 변경 포함을 확인한 뒤에만 외부에 전체 완료를 보고하고 완료 게이트를 통과합니다. 실패하면 커밋 대기로 기록하며 문서 커밋이나 검증이 보류됐으면 전체 완료로 보고하지 않습니다.
- 관련 문서의 로컬 커밋은 기본 업무 계약으로 설치하되 기존 저장소의 더 엄격한 승인·서명·훅 규칙을 보존합니다. 담당 파일만 stage하고 커밋 메시지 또는 trailer에 업무 ID를 기록합니다.
- 코드 커밋·원격 푸시·병합·배포는 해당 업무의 승인 범위를 따릅니다. 문서의 로컬 커밋과 팀 원격 공유 완료는 구분합니다.
- 여러 저장소는 원자적으로 커밋되지 않습니다. 일부 성공은 부분 완료로 기록합니다. 문서의 자기참조 커밋 SHA를 만들지 않고 최종 문서 SHA는 Git 이력과 최종 보고로 추적합니다.

정책 문구뿐 아니라 지원되는 프로젝트 시작·도구 실행·완료 검사에도 이 조건을 연결합니다. Task 없음, 미기록 브랜치 전환과 미커밋 문서의 완료 보고를 거부하도록 설계합니다. 지원되지 않는 경로는 실행 차단 미검증으로 보고하며 모든 환경에서 절대 우회 불가능하다고 주장하지 않습니다.

### 설치와 다른 정책 연동

설치 지시서는 TASK_POLICY·ARTIFACTS·SESSION_START와 Task README 템플릿을 기존 원본과 충돌 없이 연결합니다. 진입 파일의 `project-task-policy:begin/end` 블록만 관리하고 기존 Orca·모델 지침과 프로젝트 보정을 보존합니다.

Orca 정책이 있으면 dev 기준 워크트리·부모 검사는 Orca가 맡고, 이 정책은 Task 등록·브랜치 연결·업무 정본·문서 커밋을 맡습니다. 없으면 확인한 현재 프로젝트의 브랜치 규칙으로 문서 관리만 수행합니다. 단독 설치에 Orca나 Codex·Claude 양쪽 CLI를 요구하지 않습니다.

그룹의 정책 원본은 문서 저장소에서 관리하되 각 저장소에는 버전이 고정된 정책 사본·검증된 스냅샷을 제공합니다. 실제 업무 Task 정본을 각 코드 저장소에 중복 복제하지 않습니다. 다른 컴퓨터·새 워크트리에서 지침이 읽히려면 진입 파일과 관련 정책이 기준 커밋에 포함돼야 합니다.

## 업데이트와 효과 검증

업데이트할 때 GitHub 변경 이력을 확인하고 해당 설치 파일을 다시 적용합니다. 기존 파일을 백업하고 관리 영역만 갱신하며 개인 지침, 관련 없는 설정과 프로젝트 보정은 보존합니다. 세션 시작 때마다 원격 파일을 다운로드하거나 실행하지 않습니다.

대표 업무 10~15개로 첫 실행 성공률, 최종 정확성, 완료 시간, 모든 에이전트의 전체 사용량, 메인의 재작업, 승격 횟수와 통합 결함을 비교합니다. 이 저장소를 작성하면서 구현 벤치마크를 수행한 것은 아닙니다. 후보 모델의 성능 향상이 실제 업무 절약으로 이어지는지는 이 평가로 판단합니다.
